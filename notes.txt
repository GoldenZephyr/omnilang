* We are looking to define semantics for transforming or changing (PO)MDPs with explicit hierarchies
* Introducing "TSP as macroaction" has implicit hierarchy, in that we have implemented and defined going to each place "outside" of the planning domain
    * But if we want the macro action to inherit properties like "might find cup", we need to add that as a new property of the macro action
    * Instead, we would like to add "might find cup" at the lowest level of abstraction, and automatically infer the updates to the higher-level abstraction

* Traditionally, planning problems have been defined in isolation.
    * e.g., introducing a planning problem P

* We are interested in perturbations or transformations of P
    * Some perturbations are easy -- Adding a transition to the MDP with the same state space
    * Adding multiple robots is a perturbation
        * If we change the "base" MDP do we need to re-write the multi-robot MDP?
    * Changing belief dynamics is a perturbation
        * e.g., "if we are in a kitchen and we observe a new place, there might be a cup in that place"
        * How do we apply this perturbation to abstractions in a domain?

Outline of what we would to introduce and show:

Theory / Formulation:
* Especially in the LLM era, great benefit in having a model of POMDP relationships
* Formalize "perturbation"
* Handling different mappings from perception symbols (e.g., nodes in scene graph) to planning symbols (e.g., pddl objects) could be seen as a perturbation -- should explicitly represent the mapping from perception to planning concepts separately from logic internal to planning domain
* Demonstrate how writing down multi-robot planning domain is simplified with concept of "multi-robot perturbation"
    * Good example of projection / lifting between domains
* Explain that applying perturbations in domains with hierarchy isn't straightforward
* What are the semantics of perturbations in domains with hierarchy?

* How to represent connection between frontiers and exploration?
    * Start with "fully known prior" case -- no frontiers, MDP dynamics are same as fully explored case
    * next, consider "explore the world" case with no prior map
        * now we have frontiers
        * next to each frontier there might be a place
        * and next to each unobserved place there might be another frontier
        * _could_ be represented as streams -- S(frontier) -> predicted_place, T(predicted_place) -> frontier, Visit(predicted_place) -> Maybe(Place) [maybe predicted places count as real places in the planning problem?]
        * (don't want to run PDDLStream, but same idea)
        * "fully explore the world" means, "Every possible place is visited", which means "visit all predicted places" and a necessary condition for that is to visit every frontier
        * We want to be able to run the above logic automatically.
        * Once we have deduced the subgoal "visit every frontier", we want to replace with our optimization of Greedy/TSP/MCHP
        * Think of the problem as manipulating the belief space by "searching" for a counterexample and then "fixing" it
        * Forall (x: Place), (visited x) would be invalidated by a place that isn't visited. All places *in* the scene graph are visited. However, S can generate (predicted?) places that aren't visited. We must visit all of these

* (our) streams are "generators" for possible current world states
    * we want to automatically derive necessary conditions for task completion from the definition of these generators
    * How does this interpretation of streams compare to PDDLStream?
        * The semantics of the PDDLStream "placeholder" args aren't ever defined
        * our Streams are different from non-placeholder PDDLStream streams
        * They are more similar to PDDLStream placeholder streams, although we may not know if the stream output is "valid" until we take more observations

* I think there's still underdeveloped formulation about how the "problem-grounding" process composes when we compose domains. At least conceptually there's a difference between composing abstract domains and then applying to a scene representation, and applying domain transformations to a fully-grounded domain. I think these are both valid operations, and we need to define our formulation accordingly.
    * This ability to compose "problem-grounding functions" is what gives our approach its generality.

* We also need to develop our notion of stream evaluation -- there is some sort of "stream evaluation manager" that is in charge of deciding which generated scenes are relevant / calling the planner after some number of stream evaluations.
